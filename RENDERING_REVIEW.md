# Анализ рендеринга карты — 2026-11-12

## Вывод

Текущая архитектура обеспечивает быстрый GPU путь только для ограниченного набора тайлов. При его переполнении меняется весь способ отрисовки: включается дорогой CPU растр. Миникарта всегда использует CPU растр. Отмена ожидания камеры устраняет остановку управления, но повторное использование растрового изображения даёт временно недостаточную детализацию и пустые края. Чтобы одновременно получить плавность, стабильное изображение и отсутствие заметной подгрузки, необходимо заменить этот переход на постоянный GPU рендер с готовыми обзорными уровнями, независимым кешем визуальных тайлов и упреждающей загрузкой.

Это анализ текущих исходников и локальный CPU замер, не профиль запущенной игры. Предложенная архитектура ниже ещё не реализована.

## Путь кадра и установленные проблемы

| Участок | Реализация | Последствие |
| --- | --- | --- |
| Получение подробных чанков | `client.rs`: каждые 50 мс обход и сортировка всех загруженных чанков; до четырёх снимков соседства 3×3 | Работа на игровом потоке; её стоимость зависит от дальности загрузки, а не только от размеров карты |
| Получение LOD | Каждые 250 мс сортировка доступных LOD, до четырёх снимков | Дополнительные периодические затраты; нужен отдельный замер |
| Планирование | `Service` объединяет задания семплирования и пробуждения камеры в очереди из восьми элементов | Новое положение камеры записывается сразу, но тяжёлая уже начатая работа не прерывается |
| Подготовка видимости | `Cache::prepare` обходит индекс, отбирает ограниченное число записей в порядке ключей, удаляет данные за текущей областью | При недостатке памяти близкие к камере тайлы не гарантированно получают приоритет; движение назад может повторять чтение и подготовку |
| GPU атлас | Один слот 1024×1024, 4096 тайлов по 16×16 с отдельным выравниванием рядов detail/LOD | Превышение ёмкости или `paged` полностью переключает большую карту на CPU |
| Обновление атласа | Ключ включает общий `cache.clock`; изменение данных или выход за покрытие запускает `terrain_atlas` | Пересчёт освещения и упаковка всей выбранной области даже при небольшом изменении; нет устойчивых слотов и точечной инвалидации |
| Загрузка изображения | `native_mod_image` копирует весь переданный RGBA буфер в `Patch` | До 4 МиБ CPU копирования и передачи за обновление вместо небольших изменённых участков |
| CPU растр | `Cache::render`: до 1024×1024 пикселей, координаты, поиск тайла и высот соседей | Стоимость зависит от числа экранных пикселей; вращение и масштаб заставляют повторять вычисления |
| Пустота и LOD в растре | При отсутствии detail `lod_pixel` проверяет до 23 уровней для каждого пикселя | Сильно отдалённая разреженная карта может быть дороже заполненной; миллион пикселей означает до 23 миллионов проверок LOD |
| Диск в подготовке | `tile_at`/`coarse_at` могут читать и декодировать записи при промахе | В CPU пути чтение потенциально оказывается внутри пиксельного обхода; LRU ограничивает RAM, но не время кадра рабочего потока |
| LRU | Поиск старейшей записи обходом всех элементов; расчёт памяти resident также через обход | При частых вытеснениях стоимость растёт с числом записей |
| Coverage и порталы | После публикации заново строятся карты/множества, маски LOD и список порталов | Даже смена камеры без изменения земли создаёт работу, не нужную для новых пикселей |
| Сохранение | Один worker семплирует, читает, рисует и выполняет commit с обновлением индекса и синхронизацией диска | Медленный commit задерживает подготовку изображения; главному потоку диск напрямую не нужен, но видимая подгрузка запаздывает |
| Миникарта | CPU растр, размер `size * 4`, до 1024 на сторону | При размере 256 получается миллион пикселей; поворот игрока вызывает новые изображения вместо дешёвого поворота GPU геометрии |
| Переключение карт | Один общий HUD слот | Нельзя одновременно сохранять независимые готовые GPU представления миникарты и большой карты |

Исходники для проверки: `mixins/minimap_worldmap_waypoints_reworked/runtime.rs` (`Cache`, `Backing`, `Service`, `terrain_atlas`, `render`, `lod_pixel`, `coverage`), `client.rs` (`frame`, `draw`, `complete_map_view`), `lod_adapter.rs` либо соответствующий LOD адаптер в каталоге mixin. Реальный мост загрузки: экспортированный pinned `crates/horizon-client/src/game/native_hooks.rs`, функция `native_mod_image`.

## Что означает размер кеша

В ранее прочитанном пользовательском контейнере 8.1 МиБ было 1606 записей: 1172 detail и 434 LOD. Сумма полезных записей — 4 588 410 байт, средняя запись — около 2857 байт. Остальное включает выравнивание, индексы, защищённые предыдущим корнем записи и свободное место. Размер файла не определяет число пиксельных вычислений или частоту перестройки атласа.

Чистые RGBA изображения 1606 тайлов занимают примерно 1.57 МиБ. Они помещаются в существующий слот по числу тайлов. Однако RAM семантических данных (высоты, биомы, порталы, коллекции) и условие `paged` — отдельные ограничения. Нельзя делать вывод о фактическом выбранном пути по одному размеру файла: нужны счётчики режима и причин перехода.

Предыдущее объяснение про начисление 128 КиБ на каждый тайл было ошибочным: код прибавлял этот запас к уже рассчитанной фактической памяти только для проверки следующего тайла. Исправленная проверка точнее использует бюджет, но не доказывает причину тормозов данного контейнера. Реально найденная блокировка камеры на границе готового покрытия уже удалена.

## Воспроизводимый замер

Команда: `cargo test --release --locked --offline benchmark_worldmap_cpu_work -- --ignored --nocapture`.

| Ширина мира в кадре | CPU растр 1024×1024, мс на изображение |
| --- | ---: |
| 32 блока | 42.321 |
| 256 блоков | 44.344 |
| 2048 блоков | 109.005 |

Тест содержит 4096 синтетических detail тайлов, без дискового backing и реальных биомов. Усреднение — 60 изображений. При отдалении появляются пустые пиксели, для которых проверяются LOD уровни. Это подтверждает конкретную дорогую ветку, но не является измерением FPS игры.

Важный дефект интерпретации существующего бенчмарка: атлас создаётся до расширения вида и включает только малую padded область, а не все 4096 тайлов. В этом запуске он занял 262144 байта и подготовился за 2.474 мс; его обход дал 0.001–0.002 мс. Эти числа нельзя сравнивать как равнозначный полный GPU кадр с CPU растром широкого вида. Перед измерением новой архитектуры нужно исправить fixture: одинаковая видимость и покрытие, detail + LOD, и отдельно реальный кеш. GPU исполнение, отправка вершин и копирование текстур данным тестом не измеряются.

## Почему изображение меняется и появляется частями

1. Свободная камера сейчас может выйти за готовую область. Там отсутствует изображение до завершения подготовки.
2. Перепроецирование старого CPU кадра сохраняет правильные координаты, но при приближении увеличивает уже потерянные при растеризации детали; при появлении нового кадра резкость меняется.
3. Nearest и один образец на экранный пиксель при сильном уменьшении пропускают тонкие объекты. Небольшое движение камеры меняет выбранные образцы — возникают мерцание и скачки цветов.
4. LOD Horizon — приблизительные данные мира, а не готовая иерархия изображения нашей карты. Их разрешение, цвет и высота могут отличаться от detail. Подмена одного другим без устойчивого правила покрытия заметна.
5. При превышении 4096 тайлов одновременно меняются разрешение, алгоритм выборки и время подготовки. Это архитектурный скачок качества и задержки.

## Предлагаемая архитектура

### Постоянный GPU рендер обеих карт

Выделить модулю собственные текстуры/страницы через переносимый рендер Horizon. Detail, обзор и миникарта используют общие визуальные тайлы. Камера меняет матрицу, поворот и clipping; цвет земли при этом не пересчитывается. Круг миникарты вырезается shader/stencil маской, вращение выполняется на GPU. Порог количества исходных чанков не должен включать CPU растр.

Для интеграции нужны AST изменения через Horizon Mixins plan/apply, включая жизненный цикл GPU ресурсов, перезагрузку и их освобождение. Использовать доступные ограничения устройства; размер страниц и число слоёв должны подбираться переносимо. Один увеличенный фиксированный атлас лишь отодвинет нынешний предел.

### Визуальные тайлы отдельно от полного кеша

Кешировать уже освещённые цвета для отображения независимо от высот, биомов и порталов. GPU странице назначать устойчивый слот. Изменение чанка инвалидирует его визуальный тайл и соседей, чьё освещение от него зависит, затем соответствующих родителей обзорной иерархии. Передавать изменённые прямоугольники пакетами; объединять соседние обновления.

Метаданные нужны для подсказок и запросов, но не должны декодироваться заново для каждого кадра. Учитывать уникальные разделяемые payload отдельно от ссылок и ограничивать суммарную память всех кешей. Приблизительный учёт не должен сам выталкивать подходящий GPU вид в другой алгоритм.

### Готовая иерархия обзора

Строить уровни уменьшения из канонических цветов карты при изменении земли, сохранять их в производном кеше. На старте мира прогревать компактный обзор и район игрока до открытия карты. Для небольшой карты целесообразно заранее держать все её визуальные тайлы; для большой — весь компактный обзор плюс детали текущей области.

При отдалении количество отображаемых регионов должно зависеть от площади экрана, а не от всей истории исследования. Выбирать обзорный уровень по блокам на пиксель. Вблизи сохранять исходные texel и nearest, вдали использовать корректно агрегированные цвета и покрытие, с гистерезисом выбора уровня. Это не размывание подробной карты: подробные данные сохраняются, но субпиксельные объекты нельзя одновременно показать отдельно на ограниченном экране.

Агрегация должна учитывать alpha/маску покрытия, не смешивать неизвестное с чёрным и не заполнять неизвестные территории выдуманными данными. Разделять неизвестность и известную пустоту. Detail имеет приоритет над Horizon LOD, включая прозрачные известные чанки. Соседние уровни должны происходить из одной версии канонического изображения. Не применять слепой crossfade: он способен породить двоение границ и смену яркости. Нужны проверки границ тайлов, отрицательных координат и появления detail поверх LOD.

### Подготовка до движения в область

Prefetch учитывать не только текущий кадр, но и цель сглаживаемой камеры, следующий масштаб и направление перетаскивания. Сохранять запас сзади и hysteresis вытеснения, чтобы обратное движение не вызывало новые чтения. Приоритет: готовый обзор, видимая область, целевой вид, окружение.

Устаревшие задания объединять и отменять между небольшими порциями. Новые детали публиковать как согласованный набор видимого региона, сохраняя ранее готовый обзор, а не показывать отдельные появляющиеся квадраты. Это требует временного запаса памяти для старого и нового набора. Не ждать готовности всей исследованной карты ради одной области.

Для уже исследованной области такой обзор позволяет избежать пустых дыр при штатном перемещении. Абсолютное отсутствие изменения детализации при произвольном мгновенном переходе в неограниченную карту на холодном диске нельзя гарантировать с ограниченной памятью. Практическая цель — полное покрытие обзором сразу, подготовленные детали в пределах поддерживаемых скоростей камеры и отсутствие растягивания экранного скриншота.

### Независимая работа с данными

Оставить владение контейнером одному I/O worker, но отделить его от подготовки цветов и игрового потока. Чтение, приоритетные запросы, очередь принятых изменений и commit должны иметь понятные бюджеты и backpressure. Сохранение не должно задерживать использование уже готовых визуальных тайлов. При ошибке записи сохранить нынешнее правило удержания принятых несохранённых данных.

Добавить пространственный индекс по dimension/layer/region и приоритетный выбор, исключить обход всей истории на движение камеры. Заменить линейный поиск жертвы LRU на структуру с ограниченной стоимостью. Перестраивать coverage/порталы только по изменениям данных. На клиенте собирать изменившиеся чанки по уведомлениям либо вести ограниченный инкрементальный обход вместо полной сортировки каждые 50 мс.

## Порядок внедрения

1. Измерения реального пути: время игрового callback, сбор снимков, подготовка/очередь/чтение, причины перестройки, число и байты uploads, CPU/GPU кадры, возраст видимых данных. Раздельно camera-only, изменение terrain и commit.
2. Устойчивые визуальные тайлы, инкрементальное освещение и частичные uploads; собственные GPU страницы. После прогрева неподвижная земля не должна загружаться повторно от движения камеры.
3. GPU миникарта с маской и вращением; общий кеш обеих карт.
4. Сохранённый обзор, выбор уровня, spatial lookup, prefetch цели камеры и публикация готового покрытия. Удалить основной CPU fallback и зависимость качества от 4096 исходных тайлов.
5. Отделить I/O и фоновые вычисления, ограничить работу игрового callback, инкрементально обновлять индексы/метаданные. Сохранять совместимость существующего контейнера либо явно версионировать производные данные.

Пункты 2–4 вместе обеспечивают требуемое поведение; только ускорение диска, увеличение RAM или более крупный слот его не обеспечат.

## Проверка результата

Цели — критерии для измерения, а не обещанные текущие показатели:

- После прогрева перетаскивание/масштабирование не выполняют дисковые операции, CPU растеризацию или полный upload на игровом потоке. Изменение только камеры не пересоздаёт текстуру.
- При неподвижном мире плавное вращение миникарты не вызывает перезагрузку её изображения.
- На выбранном тестовом устройстве вклад мода в главный поток: ориентир p95 менее 1 мс, p99 менее 2 мс; отдельно измерить GPU и общий бюджет 16.7 мс для 60 FPS. Средний FPS без percentiles недостаточен.
- На прогретой исследованной карте нет пустых участков и видимых поочерёдно появляющихся квадратов при заданном диапазоне скоростей pan/zoom. Записать этот диапазон и измерить deadline misses.
- Нет дрожания тонких линий при отдалении, швов тайлов, просвечивания LOD через известную пустоту, сдвигов маркеров, изменения цвета при перепаковке страниц.
- Сценарии: реальный кеш 8 МиБ, более 4096 записей, большая разреженная история, низкий RAM, холодный старт, быстрый обратный drag, быстрый zoom, смена измерения, resource reload, commit и медленный диск.
- Проверять масштаб окна и GUI, 1080p/1440p/4K, круглую и квадратную миникарту, отрицательные координаты. Linux/macOS/Windows требуют собственных запусков.
- Регрессионные проверки runtime, clippy/fmt, template/stage и check/test на pinned Horizon обязательны; визуальная запись и профиль работающей игры нужны дополнительно.
